# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Repository layout

- `app/` — the actual application (StudyDesk: turns a YouTube playlist into a course with chapters, notes, AI quizzes/flashcards, streaks). All commands below run from here.
- `docs/product/` (core idea, MVP, `app-functionality-spec.md`, admin page), `docs/design/` (UI description, brand brief, page specs in `pages/`, static HTML mockups in `mockups/` that the React pages were ported from), `docs/architecture/backend-architecture.md`.
- `docs/production-readiness.md` — the launch checklist (auth, 3-course limit, ownership checks, rate limits, deployment). When asked to review it, verify each item against the code, not just its checkbox.
- `scratch/` — one-off debugging scripts, screenshots and data backups (`scratch/ui-prototype/` holds the old mockup-porting scripts). Git-ignored (root `.gitignore`); never part of the app.

## Git workflow

The repo root is this folder (`app/`, `docs/` etc. live inside it); remote `origin` is the private GitHub repo https://github.com/siddhajperiwal-hue/youtube-study-wrapper, branch `main`.

**After every code change, commit and push to GitHub** (the user's standing instruction): once a change is finished and checks pass (`npx tsc --noEmit`, `npm test`, lint on touched files), run `git add -A`, commit with a message describing what changed and why, and `git push`. One commit per finished change; don't push half-done or failing work. Before committing, check `git status` for anything that must not be pushed: `.env*` (except `app/.env.example`), `scratch/`, `node_modules/`, `.next/` are git-ignored and must stay that way.

## Commands (run in `app/`)

```bash
npm run dev                      # next dev (Turbopack), http://localhost:3000
npm run build                    # production build
npm run lint                     # eslint (next core-web-vitals + typescript)
npm test                         # vitest run (all tests)
npx vitest run src/lib/__tests__/youtube.test.ts   # single file

```

Only one `next dev` can run per project directory — a second one exits with "Another next dev server is already running".

Env vars live in `app/.env.local` (template: `app/.env.example`): Supabase URL/anon key/service-role key, `GEMINI_API_KEY`, `YOUTUBE_API_KEY`.

## Next.js version warning (from `app/AGENTS.md`)

## Architecture

**Pages are client components that fetch from internal API routes.** The three screens — dashboard (`src/app/page.tsx`), course syllabus (`src/app/course/[id]/page.tsx`), learning view (`src/app/course/[id]/learn/[videoId]/page.tsx`) — are thin `"use client"` pages (~200–550 lines) that render a skeleton, then fetch `/api/...` in `useEffect`, composing per-page hooks and components from `src/components/{dashboard,course,learning}/` (each folder has `types.ts`, `use*.ts` hooks owning state/logic, and presentational `*.tsx`). Shared pieces: `src/components/ReportModal.tsx` (configurable per page), `src/hooks/` (`useToast`, `useTheme`, `usePageVisible`, `useHasTruncatedText`). Learning page: `useYouTubePlayer` (IFrame postMessage API, smooth clock, seeking, teardown; the page owns the iframe ref and passes it in), `useNotesEditor`, `useChapterQuiz`, `useFocusTimer`, `useFocusMode`, `useStudyTracking` (heartbeat `/api/study/heartbeat` + progress saves `/api/progress`). Hooks must not return ref objects or functions that write refs — the React-compiler lint rules then treat every value read from the hook as a ref.

**Styles:** `src/app/globals.css` (theme tokens) → `src/styles/components.css` (shared UI: `.btn*`, `.deck-card`, quiz/flashcard pieces, modals, empty states; imported globally in `layout.tsx`) → page-only rules in `src/styles/{dashboard,course,learning}.css`. A class used by more than one page belongs in `components.css`: page stylesheets only load once that page is visited, so a class borrowed from another page's stylesheet is unstyled on a direct visit.

**Theming:** light/dark is a `data-theme` attribute on `<html>`, persisted in `localStorage` (`studydesk_theme`). An inline script in `src/app/layout.tsx` applies the saved theme before first paint on every page; only the dashboard has the toggle. **All `--color-*` / `--shadow-*` tokens (light and dark) live only in `src/app/globals.css`.** Page stylesheets `src/styles/{dashboard,course,learning}.css` must not redefine them on `:root`: they are injected later on client navigation and stay loaded, and an equal-specificity `:root` rule loaded later overrides `[data-theme="dark"]` (this caused "learning page turns light / toggle stops working").

**Performance model:** each Supabase round trip costs ~0.4s from the dev machine (DB time is ~1–8ms; it's network distance to the project region), so API latency ≈ 0.4s × number of sequential `await` waves. Keep routes to one wave: nested PostgREST selects (`courses → playlists → videos(video_content, video_resources)`) plus `Promise.all` for anything keyed only by request params. Page transitions rely on the client cache below rather than on fast APIs.

**Client cache (`src/lib/cache.ts`):** `fetchWithCache(url, ttl)` is an in-memory TTL cache with in-flight dedup; `getCached(url)` returns any cached value regardless of age; `prefetchData(url)` warms it and sends an `x-prefetch: 1` header. Pages render cached data immediately, then revalidate (stale-while-revalidate, ~10s freshness), and prefetch the next page's API data on hover / likely-next (course cards, chapter rows, prev/next chapter). Call `invalidateCache(prefix)` after mutations. Background refreshes must not clobber what the user is interacting with (dashboard keeps an on-screen quiz/flashcard; course page doesn't overwrite settings fields being edited).

**Auth:** Supabase Auth with email + password and Google OAuth (Google only works once the provider is enabled in the Supabase dashboard; `GoogleButton` checks `/auth/v1/settings` first so users never land on Supabase's raw error page). Pages: `/login`, `/signup`, `/forgot-password`, `/reset-password` (shared `AuthShell` + `src/styles/auth.css`; friendly error text in `src/lib/auth-messages.ts`). `src/app/auth/callback/route.ts` finishes Google sign-in, email confirmation and password-reset links (`code` → `exchangeCodeForSession`, or `token_hash`+`type` → `verifyOtp`; recovery goes to `/reset-password`). `src/proxy.ts` (Next 16's name for middleware) refreshes the session cookie on every request and does the optimistic gate: signed-out page visits → `/login?next=…`, signed-out `/api/*` → 401, signed-in visits to login/signup → `/`. Login and sign-out do a full page load (`window.location.assign`) so the in-memory client cache and pages kept mounted in `<Activity>` never carry one account's data into another; `fetchWithCache` sends a 401 to `/login`. A DB trigger (`handle_new_user` in `supabase_schema.sql`) creates the `profiles` row.

**API routes (`src/app/api/**/route.ts`)** all follow one pattern: `getEffectiveUserId()` → `if (!userId) return unauthorized()` → `createAdminClient()` → Supabase queries → hand-shaped camelCase JSON.
- `src/lib/auth-helpers.ts`: `getEffectiveUserId()` uses `supabase.auth.getClaims()` (local JWT verification; the project uses ES256 signing keys, so no Auth-server round trip) via `@supabase/ssr` cookies (`src/lib/supabase/server.ts`) and returns **null when signed out** (there is no guest user any more). Every route must check it, even though the proxy also gates `/api/*`.
- Supabase query builders are lazy: a query that is never awaited/`.then`-ed never executes (`void supabase.from(...).update(...)` is a no-op). Use `after()` from `next/server` for post-response work.
- `src/lib/supabase/admin.ts` uses the service-role key, which **bypasses RLS** — every query must filter by `user_id` (or by `course_id` already verified to belong to the user) itself. The RLS policies in `supabase_schema.sql` do not protect these routes.
- Request bodies are validated with zod schemas in `src/lib/validations.ts`.

**Data model (`app/supabase_schema.sql`):** shared, user-independent content — `playlists` → `videos` → `video_resources`, `video_content` (AI summary/topics + generation `status`), `questions`, `flashcards`. Per-user state — `courses` (a user's enrollment in a playlist; holds `quizzes_enabled`, `deadline_date`, `last_accessed_at`), `chapter_progress`, `quiz_attempts`/`answers`, `notes`, `daily_study` (streaks), `study_sessions`, `bookmarks`, `question_reports`. Chapter IDs in URLs are `videos.id` UUIDs, not YouTube IDs.

**Course import flow:** `POST /api/courses` → `extractPlaylistId` / `fetchPlaylistData` (`src/lib/youtube.ts`, YouTube Data API) → reuse or insert `playlists`/`videos`, extract links from descriptions into `video_resources` (filtering `PROMOTIONAL_DOMAINS` via `isPromotionalUrl`) → create `courses` row → `after()` starts `generatePlaylistContent()` for the whole playlist. Playlists, videos and all AI content are shared: a playlist imported again (by any user) reuses the existing rows and questions. Two simultaneous first imports race on the unique `youtube_playlist_id`; the loser (`23505`) reuses the winner's playlist.

**AI generation:** `generateContentForVideo()` in `src/lib/gemini.ts` first **claims** the video in the DB (`claimVideo`: insert-or-ignore on the unique `video_content.video_id`, or a conditional update of a `failed` / stale-`pending` row; while pending, `generated_at` holds the claim time), so concurrent requests and other server processes never generate a video twice; it returns `{ status: "skipped" }` if it can't claim. It then pulls a transcript (`youtube-transcript`), calls Gemini with a fallback cascade over `CANDIDATE_MODELS`, validates with zod, inserts questions/flashcards only if the video has none (one shared set per video), and only then marks `video_content` ready. Every attempt is logged in `generation_jobs` (status, error, timestamps); `countFailedAttempts()` reads it. Same-process calls also share one in-flight promise. `generatePlaylistContent()` (`src/lib/generation-queue.ts`) walks a playlist's non-ready videos one at a time (pauses between videos, longer after a failure; gives up on a video after `MAX_BACKGROUND_ATTEMPTS` failures), starting at a given chapter and wrapping around, one run per playlist per process. It's started by course import, `GET /api/courses/[id]` and `GET /api/courses/[id]/chapters/[videoId]` (from the current chapter) whenever any video isn't ready, never on `x-prefetch` requests. The chapter route also schedules the current chapter directly when its content is missing, pending or failed (not `failed` on prefetch). All of this runs in `after()` and assumes a long-lived server (`next start`); a serverless host would cut long playlist runs short. The quiz route (`GET /api/courses/[id]/quiz`) returns `contentStatus`; with no questions it retries generation (unless `poll=1`) and reports `generating`, and `useChapterQuiz` then shows "Generating your quiz…" and polls instead of completing the chapter without a quiz.

**Quiz option order:** the model puts the correct answer first far more than chance, so options are shuffled in code by `shuffleQuestionOptions()` (`src/lib/quiz-shuffle.ts`) before questions are inserted. It moves `correct_index` with the answer, rewrites "Option B"-style letters in explanations, strips baked-in "A)" prefixes, and leaves "None of the above"-style questions unshuffled. Grading (`/api/courses/[id]/quiz/submit`) compares against the stored `correct_index`, so never shuffle at serve time. `answers` stores only `is_correct`, so reordering stored options doesn't corrupt history.

**Pages stay mounted when hidden:** with `cacheComponents`, Next.js keeps pages you navigate away from mounted inside a hidden React `<Activity>` (`display: none`); effects clean up, but state and DOM persist and hidden pages can still re-render. Anything with side effects in the DOM must be gated on visibility. The learning page's YouTube `<iframe>` (autoplay) renders only while `usePageVisible()` (`src/hooks/usePageVisible.ts`, a `useLayoutEffect` that runs on show and cleans up on hide) is true; otherwise hidden re-renders recreated the player and its audio played behind other pages.

**Learning-page notes:** the right-hand panel (`#notesScrollCanvas`) is a stack of one page per chapter (`#chapter-page-{position}`, each at least a screen tall); only the active chapter's page holds the editor, so the panel is scrolled to that page on every chapter change — otherwise chapter 1's page is what's visible. One TipTap editor instance is reused across chapters (client navigation doesn't remount the page). Notes come from the chapter payload (`data.notes`), are loaded with `setContent(..., { emitUpdate: false })` (TipTap v3 defaults `emitUpdate` to true, which would trigger an autosave), and every save is addressed to the chapter the edit was made in (`notesTargetRef` / `pendingNotesSaveRef` in `src/components/learning/useNotesEditor.ts`). On chapter change the pending save is flushed to the old chapter, then the editor is cleared and locked until the new chapter's notes load. `invalidateCache` also discards in-flight responses for the URL, so a prefetch racing a save can't re-cache old notes. Editor-free note helpers (`notesToPlainText`, `upgradeLegacyTimestamps`, `formatTimestamp`) live in `src/lib/notes-format.ts`; only the learning page imports TipTap statically (others load it on demand), so don't import `@tiptap/*` from pages that only read notes. Timestamps in notes are a custom TipTap node `timestampBadge` (`src/lib/tiptap-timestamp.ts`, attrs `chapter`/`seconds`, rendered as `span.note-ts-badge` and handled by the learning page's `handleNotesCanvasClick`); insert nodes as JSON, never as an HTML string (it would be stored as literal text). Use `notesToPlainText()` for read-only previews. Notes are stored one row per chapter in `public.notes` (`content` = TipTap JSON). The course page's Notes tab is a read-only formatted view (each chapter links to the learning page for editing), and its "Download PDF" (`src/lib/notes-pdf.ts`) both use `renderNotesHtml()`, which renders each chapter's notes to HTML with `generateHTML`; the PDF prints a hidden iframe (user picks "Save as PDF"). Don't switch to a JS PDF library: they can't shape Devanagari, and chapter titles include Hindi.

**Learning-page extras:** the chapter route computes prev/next navigation and the "active recall" refresher (shown when `courses.last_accessed_at` is more than 24h old). `last_accessed_at` is updated by `POST /api/progress`, not by the chapter route.

**Dashboard top deck:** the Priority Course / Quick Quiz / Recall Flashcard cards are locked to a fixed size (`--deck-card-height` on `.top-deck-grid`, columns 38/31/31). Long text must be clamped (`.clamp-text` + `--clamp-lines`, marked `data-clamp`) with a `title` tooltip, never allowed to grow the card; `useHasTruncatedText` (`src/hooks/`) shows a "Full text" modal button only when something is clipped, and the modal never reveals an answer before the card does. Card state lives in `useQuickQuiz` / `useRecallFlashcard`; the next quiz question / flashcard is prefetched while the current one is shown (`useNextCardPrefetch`), and answer state is cleared in the same render that swaps in the new card. Deck cards are `position: relative` because flashcard faces/placeholders are `position: absolute` (without it they cover the whole viewport). Until `/api/dashboard/cards` responds (`cardsLoaded`), the quiz/flashcard cards show `DeckCardSkeleton`, not their empty-state copy; course prefetches wait for that and for browser idle so they don't slow the initial load.

**"Duplicate use of selection JSON ID gapcursor"** in dev (with "Could not validate `instant`") comes from a long-running `next dev` whose hot-reloaded bundle evaluated ProseMirror's gapcursor twice. It doesn't reproduce on a fresh server; restart `npm run dev` (delete `app/.next` if it persists).

**Hydration warnings:** a "tree hydrated but some attributes … didn't match" error showing inline styles expanded into empty longhands (`background-image: ""`, …) comes from a browser extension (e.g. Dark Reader) rewriting inline styles, not from the app. Verify in an extension-free/Incognito window before debugging.

## Tests

Vitest, node environment, globals on, `@` alias → `src`. Tests live in `src/**/__tests__/*.test.ts`. Route tests import the handler directly and `vi.mock` both `@/lib/supabase/admin` and `@/lib/auth-helpers`; `src/app/api/__tests__/course-routes.test.ts` has a chainable PostgREST mock (`mockSupabase`) and mocks `after` from `next/server`. No test hits a real database or network (Gemini/transcript are mocked).

UI behavior (navigation, theme, card layout) has no automated tests. It has been verified by driving headless Chrome (`C:/Program Files/Google/Chrome/Application/chrome.exe --headless=new --remote-debugging-port=...`) over CDP against the running dev server.
